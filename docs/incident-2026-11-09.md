# Webchat outage, 2026-11-09

## Finding

The chat container failed to start after the host reboot because
`oidentd.socket` had already bound public TCP/113. Docker's published ident
port is a startup dependency for the entire Lounge container, so this removed
the web frontend and Socket.IO backend together. Traefik had no running chat
container to route to. This explains both a page 404 and an existing browser's
`xhr poll error`; the latter does not establish an ISP or WebSocket problem.

Production recovered before this investigation's probes. Initial investigation
was read-only. After reviewing the server documentation, the operator explicitly
approved the ident remediation with "go ahead". The approved change and its
verification are recorded below. Transport probes never submitted an IRC
connection or message.

## Reproduction and exclusions

The live canonical route was healthy during our checks. A manually tested
`https://chat.dnbradio.com/chat` returns 404, but neither current website nor
player links there. That arbitrary route is not evidence of the incident.
EIO=3 polling returns HTTP 400, `Unsupported protocol version`; deployed
clients use EIO=4. The unchanged 2024 frontend and container provide no evidence
of an incident-day protocol upgrade. No compatibility change is proposed.

`tests/outage.test.cjs` uses the observed Lounge version locally, with Traefik
3.6.2 for compatibility with local Docker 29. Production Traefik 2.5.3
hardcodes Docker API 1.24, rejected by the local daemon. This fixture
difference limits exact-version parity, but preserves Docker provider discovery
and the startup/route failure mechanism. The deployed proxy version can be
selected with `TEST_TRAEFIK_IMAGE` on a compatible development daemon.
Docker 29 also discarded the failed container's network endpoint; the fixture
reattaches its own network when absent before testing recovery. Neither test
compatibility adjustment is proposed as a production change.
It occupies a disposable host port, makes Lounge publication fail, verifies
404 at both frontend and polling paths, and asserts the real Socket.IO
client's `xhr poll error`. Releasing that listener restores HTTP, polling,
WebSocket, and a subsequent restart. No production restart is needed to
reproduce the failure.

Validation completed in the isolated checkout on 2026-11-09:

- `npm test`: 10 unit tests passed.
- `npm run test:integration`: one integration test passed, including both
  failure assertions, both transport recovery assertions, and restart.
- `sh -n scripts/reserve-ident-port.sh` and `git diff --check`: passed.
- The script's `--check` was streamed to the production host without saving or
  applying it. It correctly failed on socket disabled/inactive and service
  enabled/inactive, confirming the remaining remediation target.
- All disposable integration containers, anonymous volumes, and networks were
  removed by the test's cleanup. Downloaded development images remain cached.

## Fix and approval packet

### Existing server documentation checked on operator follow-up

Two server-only files provide historical context absent from the GitHub clone:

- `/home/forge/apps/chat/fixidentd.sh` starts and then stops
  `oidentd.service`, then force-recreates chat using
  `/root/apps/chat/docker-compose.yml`. It is not tracked in the deployed
  repository. The referenced Compose path no longer exists. We read this
  script but did not execute it.
- `/home/forge/apps/2024-backup/znc/README.md` says ZNC ran as user `znc` on
  the host, with host oidentd bound to `49.12.202.218` so it would not conflict
  with The Lounge's ident listener.

The workaround is consistent with `oidentd.socket` declaring
`Conflicts=oidentd.service`: starting the service can stop the socket, and
stopping the service then releases the listener. It does not remove either
boot activation path, explaining why a reboot can reintroduce the conflict.
This mechanism is inferred from the script and unit definition, not a fresh
execution of the old workaround.

Current read-only checks found no ZNC process, systemd unit, `znc` account,
or installed `znc` package on this host. The historical IP is not assigned
here now. Current oidentd options (`-mf -l 10`) contain no address restriction,
and its socket listens on `[::]:113`. Therefore the documented historical
separate-IP arrangement is not the current configuration.

The recommendation to mask both host activation paths still fits the observed
host. If ZNC is restored here, give its ident service a distinct verified IP
and scope both service and socket bindings before enabling it. The host's
addresses include both `78.46.229.41` and `49.13.204.214`, which also resolves
the apparent cloud-inventory IP discrepancy noted above: they belong to the
same inspected host.

### Proposed durable remediation

`scripts/reserve-ident-port.sh` defaults to a read-only check. Its explicit
`--apply` stops and masks **both** `oidentd.socket` and `oidentd.service`, then
verifies both are masked/inactive. This removes competing boot/manual
activation paths while preserving the existing Docker ident mapping. The
observed socket-only disable left the standalone service enabled.

Recommended production change, requiring explicit operator approval:

1. Recheck `ss -ltnp 'sport = :113'`, container state, and both unit states.
   If ownership or service use has changed, reassess before applying.
2. Save the enabled/active states of both units as the rollback record.
3. On `78.46.229.41`, run the reviewed script with `--apply` as root.
4. Verify both units are masked/inactive, Docker still owns port 113, and
   the existing container's start timestamp is unchanged. Repeat root,
   polling, and WebSocket checks without connecting to IRC.

Do not restart Docker, recreate chat, change the image, or reboot. A reboot
verification is outside this packet. Rollback: unmask both units and restore
the saved states, without activating a competing listener while Docker owns
113. At investigation time the saved-state expectation is socket
disabled/inactive, standalone service enabled/inactive.

## Approved production remediation completed

On 2026-11-09 at approximately 23:34:49 UTC, following explicit operator
approval, applied the reviewed `reserve-ident-port.sh --apply` on
`78.46.229.41`. Rechecked ownership first: Docker owned TCP/113, chat was
running, and no ZNC or host oidentd process was present.

Rollback evidence and the exact applied script are retained on the server at
`/root/dnbradio-ident-fix-20261109-640d1d5/`. It contains both units' prior
states and definitions, the prior listener/container details, and the operation
timestamp. Prior states: socket disabled/inactive, service enabled/inactive.

Verified after application:

- Both `oidentd.socket` and `oidentd.service`: masked and inactive.
- Docker proxy PID 81393 still owns `78.46.229.41:113`.
- Chat remains running with the same image and unchanged start timestamp,
  `2026-11-09T23:09:35.212503246Z`.
- Public homepage returns HTTP 200 and Lounge HTML.
- Actual Socket.IO sessions connect with polling-only and WebSocket-only
  transports, then disconnect without joining IRC or sending messages.

No Docker/chat restart, image change, proxy change, DNS change, or reboot was
performed. A real reboot was not tested. Production rollback, if separately
approved, should unmask both units and restore the recorded enabled states
without starting either host ident listener while Docker owns TCP/113.

## Separate show-title investigation

This path is in `dnbradio-laravel`, not this webchat repository:

1. `LiveShowController::updateLiveShowTitle` authorizes the DJ and invokes
   `azura:update-live-title` with artist, title, and station.
2. `Azura/UpdateLiveTitle.php` sends an authenticated POST to
   `https://azura.drmnbss.org/api/station/{id}/nowplaying/update` with a
   ten-second timeout. HTTP 200 is treated as success; no later read-back is
   performed. API callers receive a failure response when the command fails;
   the website form redirects regardless of command result.
3. `Azura/FixLiveTitle.php` runs every fifteen seconds in production under
   `withoutOverlapping()`. It reads `/api/nowplaying/dnbradio`, looks up the
   streamer, and may send a replacement through `UpdateLiveTitle`.
4. Website and player normalization display `now_playing.song.title` from
   AzuraCast, with the live streamer substituted for artist.

Concrete follow-on findings in `FixLiveTitle.php`:

- It returns `Already updated` when the **previous** song artist matches the
  current DJ, even if the **current** artist is wrong. A stale current title
  can therefore remain unrepaired indefinitely for that history state.
- Streamer fields are dereferenced before checking whether lookup failed.
- It validates artist identity, not the intended show title. A matching artist
  does not establish that a manually submitted title has reached the stream.

These findings do not prove the cause of the November 9 title reports. Next
investigation should correlate a failed DJ submission's HTTP result, AzuraCast
read-back, streamer metadata updates, and scheduler output. A later source
metadata update may overwrite an accepted title, so blind retries or enforcing
the calendar title could overwrite intentional DJ metadata. Do not run these
repair commands in production during diagnosis: they write stream metadata.
